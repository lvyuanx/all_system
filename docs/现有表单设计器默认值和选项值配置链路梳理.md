# 现有表单设计器默认值和选项值配置链路梳理

## 1. 目标
梳理当前 `flow_engine` 表单设计器里“默认值”和“选项值”的配置、保存、运行时解析链路，明确现状协议和关键落点，为后续数据源类机制改造提供基线。

本文只描述当前实现，不引入新协议。

## 2. 总体链路
当前链路可以分成 6 段：

1. 设计器属性面板录入 `default_config` / `options_config`
2. 前端 JS 将字段配置归一化为节点编辑态
3. 保存时将编辑态序列化为 `form_schema.fields[*]`
4. 后端将表单库分发回各流程节点的 `form_schema`
5. 运行时接口读取节点 `form_schema` 并结合 `instance.context` 解析
6. 审批提交时再按 `context_binding` 写回上下文

## 3. 设计器录入层
入口模板在 `flow_engine/templates/flow_engine/form_designer.html`。

### 3.1 默认值配置
当前表单设计器直接暴露以下字段：

- `selectedNode.default`
- `selectedNode.default_config.source_type`
- `selectedNode.default_config.context_path`
- `selectedNode.default_config.enum_code`
- `selectedNode.default_config.db_source_code`
- `selectedNode.context_binding.read_path`
- `selectedNode.context_binding.write_path`
- `selectedNode.context_binding.write_mode`

其中 `source_type` 支持：

- `literal`
- `context`
- `enum`
- `db`

### 3.2 选项值配置
仅 `select / radio / checkbox` 组件显示选项区域，当前直接编辑：

- `selectedNode.options`
- `selectedNode.options_config.source_type`
- `selectedNode.options_config.context_path`
- `selectedNode.options_config.enum_code`
- `selectedNode.options_config.db_source_code`
- `selectedNode.options_config.fallback_to_manual`

其中 `source_type` 支持：

- `manual`
- `enum`
- `context`
- `db`

可以看到，当前设计器仍然是“字段上堆配置”的方式，而不是统一的数据源抽象。

## 4. 前端编辑态归一化
核心逻辑在 `oss/static/flow_engine/js/form_designer.js`。

### 4.1 默认值归一化
`normalizeDefaultConfig` 会把节点上的原始 `default_config` 归一化成固定结构：

- `source_type` 默认是 `literal`
- `value` 默认回填为字段 `default`
- `context_path` / `enum_code` / `db_source_code` 默认为空串
- `fallback_value` 默认是空串

这意味着：

- 即使后端没存 `default_config`，前端编辑态里也总会得到一份默认结构
- `literal` 模式下，`default_config.value` 与字段顶层 `default` 实际存在重叠

### 4.2 选项值归一化
`normalizeOptionsConfig` 会把 `options_config` 归一化为：

- `source_type` 默认 `manual`
- `context_path` / `enum_code` / `db_source_code` 默认空串
- `label_key` 默认 `label`
- `value_key` 默认 `value`
- `fallback_to_manual` 默认 `true`

如果字段是选项型组件，但没有手工选项，前端会补一个空选项行，保证 UI 可编辑。

### 4.3 节点归一化结果
`normalizeNode` 最终把字段节点整理为下面几类与本任务相关的状态：

- 顶层字段值：`default`、`options`
- 默认值配置：`default_config`
- 上下文绑定：`context_binding`
- 选项来源配置：`options_config`

也就是说，当前前端编辑态同时保留“顶层字段值 + 配置对象”两套信息。

## 5. 保存序列化链路
### 5.1 前端序列化
`buildPayloadNode` 负责把编辑态转成后端保存结构。

默认值部分的现状：

- 顶层 `default` 只要非空就直接写入 payload
- `default_config` 只有在“不是纯 literal 默认态”时才写入
- 如果只是普通固定值，并且没有上下文/枚举/数据库/兜底配置，最终可能只落顶层 `default`

选项值部分的现状：

- 顶层 `options` 始终按数组写入
- `options_config` 只有在“不是默认 manual 态”时才写入
- 若是动态选项但允许回退，仍会同时保留顶层 `options`

这说明当前协议天然是“静态字段值 + 可选动态配置”的叠加模式，不是单一来源模式。

### 5.2 保存接口
`saveFormLibrary` 会调用：

- `POST /flow_engine/form_library_save`

请求体核心是：

```json
{
  "flow_id": 1,
  "forms": [
    {
      "code": "xxx",
      "name": "xxx",
      "description": "",
      "order": 0,
      "fields": []
    }
  ]
}
```

### 5.3 后端持久化
后端入口在 `flow_engine/views/flow_form_library_save_view.py`。

当前保存策略：

- 先对整份表单库做 `normalize_form_library`
- 以开始节点或第一个节点作为宿主节点，注入 `__form_library`
- 其他节点只保留自身 `form_schema`，去掉 `__form_library`
- 如果节点通过 `__form_ref_code` 关联表单库，则用对应表单的 `fields` 覆盖节点字段定义

因此，默认值和选项值最终落地位置仍然是每个节点自己的 `form_schema.fields[*]`。

## 6. 运行时解析链路
### 6.1 运行时入口
运行时入口在 `flow_engine/views/flow_form_runtime_resolve_view.py`：

- 先读取当前节点的 `form_schema`
- 去掉 `__ui`、`__form_library`
- 调用 `resolve_form_runtime(...)`

### 6.2 选项值解析
选项解析在 `flow_engine/utils/form_runtime_util.py` 的 `_resolve_field_options`。

当前规则：

- 先把顶层 `options / choices / enum` 归一化为手工选项
- 再读取 `options_config.source_type`
- `manual` 或空值时直接返回手工选项
- `enum` 时走 `resolve_enum_options`
- `context` 时从 `instance.context` 的 `context_path` 取值
- `db` 时走 `_resolve_db_options`
- 动态结果为空时，如果 `fallback_to_manual=True`，回退到手工选项

结论：

- 顶层 `options` 是动态选项失败时的重要兜底来源
- 运行时并不要求动态选项和静态选项二选一

### 6.3 默认值解析
默认值解析分两层：

1. `resolve_form_runtime` 先检查上下文已有值
2. 没有上下文值时，再调用 `_resolve_default_from_config`

当前优先级实际为：

1. `context_binding.read_path` 指向的上下文值
2. 若未命中，再回退字段 `key`
3. 若仍未命中，再按 `default_config.source_type` 解析
4. 若解析失败，再走 `default_config.fallback_value`
5. 若还没有，再回退顶层 `default`
6. 最后按组件类型补空值

`_resolve_default_from_config` 内部支持：

- `literal`
- `context`
- `enum`
- `db`

其中 `enum` 模式的默认值来源是：

- 优先枚举项里 `default=true`
- 若没有默认项，则回退已解析选项的第一个值

### 6.4 写回链路
审批提交后的上下文写回在 `build_context_updates_from_form_data`。

当前规则：

- 根据字段 `context_binding.write_path` 决定写入目标
- `write_mode=overwrite` 时直接覆盖
- `write_mode=merge_if_absent` 时只在目标路径没有值时写入
- 如果字段没有 `context_binding`，则默认写到字段 `key`

这说明默认值读取和提交流程写回已经通过 `context_binding` 串起来，但设计器配置仍较分散。

## 7. 当前实现中的几个关键特点
### 7.1 配置重复存在
默认值和选项值都存在“顶层字段值 + 配置对象”的双轨结构：

- 默认值：`default` + `default_config`
- 选项值：`options` + `options_config`

### 7.2 设计器与运行时并不完全同构
设计器预览 `buildPreviewFormData` 只会读取顶层 `default`，不会模拟：

- `default_config.context`
- `default_config.enum`
- `default_config.db`
- `options_config` 的动态解析

因此设计器预览更接近“静态表单预览”，不等于真实运行时结果。

### 7.3 表单设计器与流程设计器有一套近似重复逻辑
`flow_engine/templates/flow_engine/flow_designer.html` 中也存在同类：

- `normalizeDefaultConfig`
- `normalizeOptionsConfig`
- 默认值/选项来源表单项

这意味着后续改协议时，至少要同时处理：

- 表单设计器
- 流程设计器节点字段配置
- 运行时解析工具

## 8. 现状结论
当前表单设计器关于默认值和选项值的链路，本质上是以下模式：

- 前端通过若干分散字段录入配置
- JS 归一化为编辑态
- 保存时序列化为 `form_schema.fields[*]`
- 运行时用 `form_runtime_util.py` 按 `source_type` 做解析
- 静态值仍作为重要兜底和兼容手段长期存在

这套实现已经具备：

- 固定值
- 上下文
- 枚举
- 数据库
- 失败回退
- 提交写回

但问题也很明显：

- 协议分散在字段顶层和多个 config 对象里
- 表单设计器、流程设计器、运行时解析逻辑存在重复
- 设计器预览与真实运行时结果不一致
- 扩展一个新来源时，需要同时改前端录入、序列化和后端解析

这也是后续“数据源类机制”需要收敛的核心背景。
