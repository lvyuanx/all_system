# core

## 模块定位
- `core` 是这套系统的框架核心层。
- 它的设计目标是高通用、低业务耦合，并且应当具备可移植性。
- 理想状态下，`core` 中的大部分能力都可以迁移到其他 Django 系统中复用。

## 子模块说明
- `auth/`
  - 用户、登录、权限、认证相关基础能力
- `common/`
  - 公共模型、公共 API、工具能力、管理命令
- `ninja_extra/`
  - 项目自己的 API 框架层
- `middlewares/`
  - 全局请求处理能力
- `admin_extra/`
  - 后台增强能力
- `utils/`
  - 核心工具
- `conf/`
  - 默认配置与框架配置常量
- `exceptions/`
  - 基础异常体系
- `crypto/`
  - 加密相关能力
- `logging/`
  - 日志相关能力

## 通用约定
- `core` 不应承载具体业务语义。
- 如果某个能力只服务单一业务模块，应优先放到对应业务 app，而不是放进 `core`。
- 在 Django template 中使用 Vue 时，统一沿用 `[[ ]]` 作为插值分隔符，避免和 Django 的 `{{ }}` 冲突。
- 单个文件尽量不要超过 `500` 行；如果明显超出，应优先按职责拆分。

## 修改约束
- 修改 `core` 前，先判断需求是不是“框架级通用能力”。
- 如果改动会影响：
  - 认证
  - 中间件
  - API 框架
  - 全局异常
  - 全局响应结构
  应视为高影响改动，必须谨慎处理。
- 对 `core.ninja_extra` 的改动尤其要慎重，因为它会影响全项目 API 层。

## 验证建议
- 优先做全局影响评估，再做代码修改。
- 至少检查：
  - Django 是否能正常启动
  - 后台页面是否正常
  - API 是否正常挂载
  - 认证链路是否正常
